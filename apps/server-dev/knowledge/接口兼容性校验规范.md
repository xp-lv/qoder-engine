# 接口兼容性校验规范

## 核心原则

4 个设计角色并行工作时，接口兼容性是最大风险。兼容性审核师必须验证四份设计文档之间的接口定义完全一致。

## 校验矩阵

### 1. 数据层 ↔ 后端 接口
| 检查项 | 说明 |
|--------|------|
| 表结构 ↔ ORM 模型 | 后端设计中引用的数据模型必须与数据层表结构一致 |
| 字段名一致性 | 后端代码中的字段名必须与数据库表字段名完全匹配 |
| 索引覆盖 | 后端高频查询必须在数据层有对应索引 |

### 2. 后端 ↔ 前端 接口
| 检查项 | 说明 |
|--------|------|
| API 路径 | 后端定义的路由路径必须与前端调用的路径完全一致 |
| 请求/响应字段 | 后端返回的 JSON 字段必须与前端期望的字段一一对应 |
| HTTP 方法 | GET/POST/PUT/DELETE 使用一致 |
| 认证方式 | 后端认证中间件必须与前端请求头中携带的 Token 一致 |
| 错误码 | 后端错误码必须与前端处理逻辑检查的错误码一致 |

### 3. 后端 ↔ Ext 接口
| 检查项 | 说明 |
|--------|------|
| API 路径 | Ext 调用的 API 路径必须与后端定义的路由一致 |
| 通信协议 | REST/WebSocket 的选择必须在两份设计中明确且一致 |
| CORS 配置 | 后端必须允许 Ext 的 origin 访问 |
| 认证 | Ext 的认证方式必须与后端认证系统匹配 |

### 4. 前端 ↔ Ext 接口
| 检查项 | 说明 |
|--------|------|
| 消息协议 | postMessage/CustomEvent 协议必须一致 |
| 数据格式 | 前端发送给 Ext 的数据结构必须与 Ext 期望的结构一致 |
| 功能边界 | 哪些功能在前端做、哪些在 Ext 做，必须划分清晰 |

## verdict 判定规则

> verdict 规则由 skill.md 的 verdict 语义表定义，此处不重复。

### ✅ 正例：接口完全一致
- 后端定义 `POST /api/users`，请求体含 `{name: string, email: string}`
- 前端调用 `POST /api/users`，请求体含 `{name: string, email: string}`
- 字段名、类型、路径完全匹配（无兼容性问题）

### ❌ 反例：字段名大小写不一致
- 后端定义响应体 `{user_id: number}`（snake_case）
- 前端期望响应体 `{userId: number}`（camelCase）
- 字段名不一致 → severity: high
