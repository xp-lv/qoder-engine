# 后端架构质量原则

> 本文档是后端设计师和后端工程师的**质量北极星**。架构决策必须以此为准绳，红队审查以此为对抗基准。

## 核心信条

**后端的价值在于业务逻辑的清晰表达，不在于技术的炫技。最好的架构是让新人 10 分钟能看懂的架构。**

---

## 第 1 原则：领域驱动——按业务能力划分，而非技术分层

### 为什么
传统的 Controller-Service-Repository 分层是**技术维度的切分**，导致加一个功能要改 3 个目录。领域驱动（DDD）按**业务能力**划分模块，一个功能在一个模块内闭环。

### 怎么做
```
# ❌ 技术分层（加功能要改 3 层）
src/
  controllers/    # 所有 Controller 混在一起
  services/       # 所有 Service 混在一起
  repositories/   # 所有 Repository 混在一起

# ✅ 领域模块化（加功能只加一个模块）
src/
  modules/
    user/          # 用户领域：Controller+Service+Repository+Model 全在这
      user.controller.ts
      user.service.ts
      user.repository.ts
      user.model.ts
      user.dto.ts
    order/         # 订单领域
      ...
    shared/        # 跨领域共享：工具/类型/常量
```

- 每个**领域模块**是独立的业务单元，高内聚低耦合
- 模块之间通过**显式接口**通信，不直接 import 对方内部实现
- 新人看目录结构就能理解系统有哪些业务领域

## 第 2 原则：依赖倒置——依赖抽象，不依赖具体

### 为什么
如果 Service 直接 import Repository 的实现类，换数据库就要改 Service。依赖倒置让**核心业务逻辑不依赖基础设施**。

### 怎么做
```
// 领域层定义接口（不依赖任何框架）
interface IUserRepository {
  findById(id: UserId): Promise<User | null>
}

// Service 依赖接口
class UserService {
  constructor(private repo: IUserRepository) {}  // 依赖抽象
}

// 基础设施层实现接口（依赖框架）
class PrismaUserRepository implements IUserRepository {
  constructor(private prisma: PrismaClient) {}
  async findById(id) { return this.prisma.user.findUnique(...) }
}

// 组装在入口文件
const repo = new PrismaUserRepository(prisma)
const service = new UserService(repo)
```

- **依赖方向**：modules → shared/interfaces，绝不反过来
- **测试友好**：Mock 接口即可测试 Service，不需要真实数据库
- **可替换**：换 ORM / 换数据库 / 换消息队列，只改基础设施层

## 第 3 原则：接口即契约——先定接口，再写实现

### 为什么（给设计师）
API 设计文档不是"写完代码再补的文档"，而是"写代码前先定的契约"。契约一旦确定，前端/Ext/后端可以并行开发。

### 怎么做
- API 设计文档必须包含：路径、方法、请求体 Schema、响应体 Schema、错误码、认证要求
- 请求/响应用 **DTO（Data Transfer Object）** 明确定义，与领域模型分离
- 错误响应格式统一：`{ "error": { "code": "USER_NOT_FOUND", "message": "..." } }`
- API 版本化：`/api/v1/users`，而非 `/api/users`

## 第 4 原则：单一职责——一个模块/函数/类只做一件事

### 为什么
God Object（上帝对象）是代码腐烂的根源。一个 500 行的 Service 谁都不敢改。

### 怎么做
- **模块职责**：一个领域模块只负责一个业务领域（User 模块不管 Order 的事）
- **类职责**：一个类只有一个变化的原因（SRP）
- **函数职责**：一个函数只做一件事，函数名能完整描述它做什么
- **判断标准**：如果你无法用一个短语描述函数的职责，说明它做了太多事

### 决策框架与检查清单
| 指标 | 红线 | 理由 |
|------|------|------|
| 函数行数 | ≤ 50 行 | 超过说明职责过多 |
| 嵌套层数 | ≤ 3 层 | 超过说明逻辑复杂需拆分 |
| 函数参数 | ≤ 5 个 | 超过考虑用对象封装 |
| 文件行数 | ≤ 300 行 | 超过考虑拆分模块 |
| 圈复杂度 | ≤ 10 | 超过说明条件分支过多 |

## 第 5 原则：错误处理——用类型表达失败，而非异常控制流

### 为什么
用 try-catch 控制业务流程会导致控制流跳跃、难以追踪。用 Result/Either 类型让失败成为返回值的一部分。

### 怎么做
```
// ❌ 用异常控制业务流程
try {
  const user = await getUser(id)
} catch (e) {
  if (e.code === 'NOT_FOUND') return res.status(404)
}

// ✅ 用 Result 类型表达可能失败
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }

const result = await userService.findById(id)
if (!result.ok) {
  return res.status(mapErrorToStatus(result.error))
}
return res.json(result.value)
```

- **业务错误用 Result**：用户不存在、余额不足、权限不够
- **系统异常才用 throw**：数据库连接失败、OOM、代码 bug
- **全局错误中间件兜底**：捕获所有未处理异常，返回统一 500 响应

## 第 6 原则：配置即代码——环境变量是第一公民

### 为什么
硬编码的端口/密钥/数据库地址是部署灾难。

### 怎么做
- 所有环境相关的值用环境变量：`PORT` / `DATABASE_URL` / `JWT_SECRET`
- 启动时校验必需的环境变量，缺失则拒绝启动（fail fast）
- 提供默认值给开发环境（如 PORT 默认 3000）
- 配置集中管理：一个 `config.ts` 文件导出所有配置

## 质量红线（绝对不做）

| 红线 | 理由 |
|------|------|
| Controller 直接操作数据库 | 绕过了 Service 层，业务逻辑无处安放 |
| Service 返回 HTTP 状态码 | Service 不应该知道 HTTP 的存在 |
| 业务逻辑写在中间件 | 中间件是横切关注点（日志/认证/CORS），不是业务 |
| 循环依赖 | A 依赖 B，B 又依赖 A，说明职责划分有误 |
| 密钥/密码硬编码 | 安全灾难，必须用环境变量 |
| 不处理 Promise rejection | 未捕获的 rejection 会导致进程崩溃 |
