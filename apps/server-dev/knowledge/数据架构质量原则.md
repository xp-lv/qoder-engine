# 数据架构质量原则

> 本文档是数据层设计师和数据层工程师的**质量北极星**。设计决策必须以此为准绳，红队审查以此为对抗基准。

## 核心信条

**数据结构比代码更难改变。设计时要想清楚三年后的数据规模和业务演进。**

改一行代码只需要一个 PR，改一个表结构可能需要数据迁移、停机、兼容旧数据。因此数据层的设计必须有前瞻性。

---

## 第 1 原则：范式优先，反范式必须有理由

### 为什么
3NF 消除数据冗余和更新异常，是数据完整性的基石。但过度范式化会导致查询性能下降（多表 JOIN）。

### 怎么做
- **默认遵循 3NF**：每张表只依赖主键，不存在传递依赖
- **反范式是特权，不是权利**：如果反范式，必须在设计文档中注明"为什么反范式"（如：某报表查询需要 5 表 JOIN，性能不可接受）
- **反范式的安全做法**：用物化视图或缓存层，而非直接在主表冗余字段

### 决策框架与检查清单
```
查询性能差 → 先优化索引 → 再考虑读副本 → 最后才考虑反范式
反范式时 → 冗余字段必须标记为 [denormalized] → 必须有同步机制说明
```

## 第 2 原则：为扩展性预留结构

### 为什么
系统演进时，数据结构变更成本最高。好的设计让"加字段""加表""加关系"变成低成本操作。

### 怎么做
- **审计字段是标配**：每张业务表必须有 `created_at` / `updated_at` / `deleted_at`（软删除）
- **软删除优先**：用 `deleted_at IS NULL` 代替 `DELETE`，保留数据可追溯
- **枚举用查找表**：状态/类型等枚举值用独立的查找表（lookup table），不用数据库 CHECK 约束或魔法数字
- **UUID 主键选项**：如果业务有分布式或合并需求，考虑 UUID（权衡：索引性能 vs 全局唯一）
- **多态关系慎用**：避免 `entity_type + entity_id` 的多态关联，改用显式外键或关联表

### 决策框架与检查清单
- [ ] 新增一个字段需要改几处？（好的设计：只加 migration）
- [ ] 新增一种实体类型需要改几表？（好的设计：只加新表）
- [ ] 数据量增长 10 倍后还能工作吗？（考虑分表/分区的预判）

## 第 3 原则：索引是性能的杠杆，也是写入的负担

### 为什么
索引让查询快 1000 倍，但每个索引让写入慢一分。盲目加索引是新手最常犯的错误。

### 怎么做
- **索引跟着查询走**：先分析高频查询的 WHERE / JOIN / ORDER BY 条件，再决定索引
- **复合索引顺序**：按区分度从高到低排列（如 `(user_id, status)` 而非 `(status, user_id)`）
- **覆盖索引**：高频查询考虑覆盖索引（索引包含所有查询字段，避免回表）
- **索引数量上限**：单表索引不超过 5-6 个，超过需要审视查询模式

## 第 4 原则：Repository 模式——数据访问的唯一出口

### 为什么（给工程师）
ORM 模型（如 Prisma Model / TypeORM Entity）是**基础设施细节**，不应该泄漏到业务逻辑中。Repository 模式将数据访问抽象为接口，让业务逻辑可测试、可替换。

### 怎么做
```
// ❌ 错误：Service 直接调用 ORM
async function getUser(id) {
  return await prisma.user.findUnique({ where: { id } })
}

// ✅ 正确：通过 Repository 接口
interface UserRepository {
  findById(id: string): Promise<User | null>
  save(user: User): Promise<void>
}

// Service 只依赖接口
class UserService {
  constructor(private userRepo: UserRepository) {}
}
```

- Repository 接口定义在领域层，实现在基础设施层
- 单元测试可以 Mock Repository，不依赖真实数据库
- 未来从 PostgreSQL 换成 MongoDB，只改 Repository 实现，业务逻辑零改动

## 第 5 原则：迁移脚本是代码，需要版本治理

### 为什么
数据库迁移是不可逆操作（DROP COLUMN 数据就没了）。迁移脚本必须像代码一样有版本、可审查、可回滚。

### 怎么做
- **每个迁移必须可回滚**：up() 创建表，down() 必须删除表
- **迁移不可修改**：已执行的迁移文件永远不改，新需求写新迁移
- **破坏性操作分步走**：先加新字段 → 迁移数据 → 删旧字段（分 3 个迁移，不一步到位）
- **命名有时间戳**：`20260725_001_add_user_avatar.ts` 而非 `v1.ts`

## 第 6 原则：配置即代码 + 事务完整性

### 为什么
数据库连接配置和事务管理是数据层稳定运行的基石。硬编码的连接字符串无法跨环境部署，缺少事务的写操作会导致数据不一致。

### 怎么做
- **环境变量管理配置**：`DATABASE_URL` / `DB_HOST` / `DB_PORT` 等全部用环境变量，启动时校验必需变量，缺失则 fail fast
- **配置集中管理**：一个 `config.ts` 或 `datasource.ts` 文件导出所有数据库配置
- **写操作包裹在事务中**：多表写入/级联更新必须用事务，确保原子性（全部成功或全部回滚）
- **事务隔离级别明确**：默认 Read Committed，关键业务场景考虑 Serializable

### 决策框架与检查清单
- [ ] 数据库连接参数是否全部来自环境变量（非硬编码）？
- [ ] 启动时是否校验了 DATABASE_URL 等必需变量？
- [ ] 写操作是否包裹在事务中（含多表级联写入）？

## 质量红线（绝对不做）

| 红线 | 理由 |
|------|------|
| 不存储明文密码 | 安全灾难，必须 bcrypt/argon2 哈希 |
| 不用 `SELECT *` | 新增字段会破坏现有代码，显式列出字段 |
| 不用 TEXT/JSON 存结构化数据 | 无法索引、无法约束、无法迁移，用正规表 |
| 不在数据库存文件内容 | 用文件系统/对象存储，数据库只存路径 |
| 不用 float 存金额 | 用 decimal/numeric，float 有精度问题 |
| 外键关系不留孤儿记录 | 用 ON DELETE CASCADE 或应用层保障 |
