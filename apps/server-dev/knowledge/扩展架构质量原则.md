# 扩展架构质量原则

> 本文档是 Ext设计师和Ext工程师的**质量北极星**。设计与实现决策必须以此为准绳，红队审查以此为对抗基准。
>
> **重要**：此处的"扩展"指 **Qoder 原生插件**（plugin.json + hooks + 后台采集脚本），不是 Chrome 浏览器扩展。Qoder 原生插件运行在 Qoder IDE（VSCode fork / Electron）内部，通过 plugin.json 声明、hooks 生命周期钩子驱动、后台 Node.js 脚本执行采集逻辑。

## 核心信条

**Qoder 原生插件寄生在用户的 IDE 中，任何资源滥用都是对用户信任的背叛。一个好的插件应该"轻量、安全、随 IDE 启停"。**

插件的后台采集进程运行在用户的机器上，CPU 占用、内存泄漏、僵尸进程都会直接影响 IDE 体验。插件必须是"好客人"——IDE 开时工作，IDE 关时消失。

---

## 第 1 原则：plugin.json 声明式注册——遵循 Qoder 插件规范

### 为什么
Qoder 原生插件通过 `~/.qoder/plugins/` 目录管理，plugin.json 是插件的唯一身份证。不遵循规范的插件无法被 Qoder 加载。

### 怎么做
- **plugin.json 必须包含必需字段**：`name`、`version`、`displayName`、`description`
- **marketplaceName 标识来源**：本地插件用 `"local"`，商店插件用商店名
- **skills/hooks/commands 路径必须存在**：声明的路径指向的文件必须真实存在
- **logo 资源存在**：声明的 logo 路径必须指向真实文件

### plugin.json 最小结构
```json
{
  "name": "qoder-monitor-collector",
  "displayName": "Qoder Monitor Collector",
  "version": "1.0.0",
  "description": "采集本机 Qoder 运行信息并周期上报到监控服务器",
  "descriptionZh": "采集本机 Qoder 运行信息并周期上报到监控服务器",
  "author": { "name": "Qoder Monitor" },
  "keywords": ["qoder-plugin", "monitor", "collector"],
  "category": "Productivity",
  "hooks": "./.qoder-plugin/qoder-hooks.json",
  "logo": "./assets/logo.svg",
  "defaultEnabled": true,
  "marketplaceName": "local"
}
```

## 第 2 原则：hooks 生命周期驱动——SessionStart 拉起、Stop 清理

### 为什么
Qoder 原生插件不是常驻服务，而是由 IDE 生命周期事件驱动的。hooks 定义了插件在何时被激活、何时被清理。不正确管理生命周期会导致僵尸进程、端口泄漏。

### 怎么做
- **SessionStart 拉起采集进程**：在 `qoder-hooks.json` 中声明 SessionStart hook，执行启动脚本
- **Stop 清理采集进程**：声明 Stop hook，执行优雅关闭脚本
- **`${QODER_PLUGIN_ROOT}` 环境变量**：Qoder 会注入插件根目录路径，脚本中用此变量定位资源

### qoder-hooks.json 结构
```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"${QODER_PLUGIN_ROOT}/bin/collector.sh\" start",
            "timeout": 15
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"${QODER_PLUGIN_ROOT}/bin/collector.sh\" stop",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

### 决策框架与检查清单
- [ ] SessionStart hook 是否声明？
- [ ] Stop hook 是否声明？
- [ ] 启动脚本是否用 `${QODER_PLUGIN_ROOT}` 定位资源？
- [ ] hook timeout 是否合理（start ≤ 15s，stop ≤ 5s）？

## 第 3 原则：后台采集进程管理——可启停、不泄漏

### 为什么
采集器是一个后台 Node.js 进程，通过 SessionStart hook 拉起。如果进程管理不规范，会导致：僵尸进程（IDE 关了进程还在）、重复启动（多次 SessionStart）、无法优雅关闭。

### 怎么做
- **PID 文件管理**：启动时写 PID 文件，停止时读 PID 文件发送 SIGTERM
- **幂等启动**：启动前检查 PID 文件，若进程已存活则跳过
- **优雅关闭**：收到 SIGTERM/SIGINT 时，停止定时器、发送最后一条数据、清理资源
- **setInterval 定时采集**：Node.js 后台进程用 setInterval（非 chrome.alarms）
- **内存控制**：采集脚本内存占用 ≤ 50MB，不缓存历史数据

### 进程管理脚本模板（collector.sh）
```bash
#!/bin/bash
PLUGIN_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
PID_FILE="$PLUGIN_ROOT/.collector.pid"
NODE_BIN="${NODE_BIN:-node}"

case "$1" in
  start)
    if [ -f "$PID_FILE" ] && kill -0 "$(cat $PID_FILE)" 2>/dev/null; then
      echo "Collector already running (PID: $(cat $PID_FILE))"
      exit 0
    fi
    "$NODE_BIN" "$PLUGIN_ROOT/bin/collector.js" &
    echo $! > "$PID_FILE"
    ;;
  stop)
    if [ -f "$PID_FILE" ]; then
      PID=$(cat "$PID_FILE")
      kill "$PID" 2>/dev/null
      rm -f "$PID_FILE"
    fi
    ;;
esac
```

### 决策框架与检查清单
- [ ] 是否有 PID 文件管理？
- [ ] 启动是否幂等（重复 SessionStart 不会创建多实例）？
- [ ] Stop hook 是否能正确杀死进程？
- [ ] setInterval 是否在收到 SIGTERM 时清理？

## 第 4 原则：采集数据真实性——采集系统级指标，不伪造

### 为什么
采集器的价值在于提供**真实的系统运行数据**。伪造数据让监控系统失去意义。采集器应读取操作系统级别的真实指标。

### 怎么做
- **hostname**：`os.hostname()`
- **qoderVersion**：从 Qoder 进程信息或 product.json 读取
- **status**：检测 Qoder 进程是否存活（`running`/`idle`/`error`）
- **uptime**：从 PID 文件或进程启动时间计算
- **cpuUsage**：`os.loadavg()` 或 `/proc/stat`（Linux）
- **memUsage**：`process.memoryUsage()` 或 `/proc/meminfo`（Linux）
- **workspaceCount**：扫描 Qoder 工作区目录数量

### 决策框架与检查清单
- [ ] 每个采集字段是否有真实数据来源（非硬编码/随机）？
- [ ] 采集失败时是否有降级策略（如 null 而非崩溃）？
- [ ] 采集频率是否合理（建议 10-60 秒）？

### ❌ 反例 vs ✅ 正例
```javascript
// ❌ 伪造采集数据
const report = {
  hostname: 'my-pc',           // 硬编码
  cpuUsage: Math.random() * 100, // 随机伪造
  memUsage: 50.0,              // 固定值
};

// ✅ 真实采集系统指标
const os = require('os');
const report = {
  hostname: os.hostname(),           // 真实主机名
  cpuUsage: os.loadavg()[0] * 100 / os.cpus().length, // 真实 CPU 负载
  memUsage: (1 - os.freemem() / os.totalmem()) * 100,  // 真实内存使用率
};
```

## 第 5 原则：上报通信——REST POST + 指数退避重试

### 为什么
采集数据通过 HTTP POST 上报到后端服务器。网络不稳定、服务器重启都会导致上报失败。必须有重试机制保证数据最终到达。

### 怎么做
- **POST /api/reports**：按统一接口文档的 DTO 格式上报
- **指数退避重试**：失败后 1s → 2s → 4s → 8s → 放弃本轮，下一轮重新采集
- **超时控制**：单次请求超时 5 秒（AbortController）
- **不上报缓存积压**：失败就放弃本轮（非关键监控数据，不积压）

### 决策框架与检查清单
- [ ] 上报 DTO 格式是否与统一接口文档一致？
- [ ] 是否有超时控制（非无限等待）？
- [ ] 是否有指数退避重试？
- [ ] 采集 instanceId 是否持久化（重启后不变）？

## 第 6 原则：配置管理——用户可配置采集目标和上报地址

### 为什么
不同用户的监控服务器地址不同。采集频率也应可调。硬编码配置让插件无法复用。

### 怎么做
- **配置文件**：`config.json` 存放服务器地址、采集频率、instanceId
- **首次启动生成默认配置**：若配置文件不存在，生成随机 instanceId + 默认服务器地址
- **配置项**：
  ```json
  {
    "serverUrl": "http://localhost:3000",
    "collectIntervalSec": 30,
    "instanceId": "auto-generated-uuid"
  }
  ```
- **instanceId 持久化**：首次生成后写入配置文件，后续读取（保证同一机器 instanceId 不变）

## 第 7 原则：零侵入——不修改 IDE 行为，不注入 UI

### 为什么
采集器是"观察者"，不是"参与者"。它只读取系统信息并上报，不应修改 IDE 的任何行为、注入 UI 元素、或影响编辑体验。

### 怎么做
- **不修改 Qoder 配置**：不修改 settings.json、keybindings.json
- **不注入 UI**：不创建 WebView、StatusBar、面板
- **不拦截 IDE 事件**：不监听文件保存、编辑器切换等
- **静默运行**：用户唯一可见的是进程列表中的 collector 进程

## 质量红线（绝对不做）

| 红线 | 理由 |
|------|------|
| 僵尸进程（Stop hook 不杀进程） | IDE 关了进程还在，浪费资源 |
| setInterval 不清理 | 收到 SIGTERM 后定时器继续跑，进程无法退出 |
| 硬编码服务器地址 | 不同用户无法复用 |
| 伪造采集数据 | 监控系统失去意义 |
| 采集进程内存 > 100MB | 资源滥用，影响 IDE 性能 |
| 修改 IDE 配置/注入 UI | 采集器是观察者，不是参与者 |
| 采集频率 < 5 秒 | 过于频繁的采集和上报会增加服务器负载 |
| 上报失败时无限重试 | 应指数退避，最多重试 4 次后放弃本轮 |
