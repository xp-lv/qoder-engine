# 需求闭环准则

## 核心原则

需求确认的目标不是"记录用户说了什么"，而是"构建一个系统闭环"——让下游 4 个设计角色拿到需求后，能独立工作且接口天然兼容。

## 闭环需求必备六要素

### 1. 技术栈选型（★ 全局决策，所有下游必须遵守）
- 后端语言+框架（如 Node.js + Express / Python + FastAPI / Go + Gin）
- 数据库（PostgreSQL / MySQL / SQLite）
- ORM（Prisma / TypeORM / SQLAlchemy）
- 前端框架（React / Vue / Svelte）
- 统一端口约定（后端 API 端口，如 3000）
- Ext 通信方式（REST API / WebSocket）

### 2. 功能边界（做什么 / 不做什么）
- 功能清单（F-001, F-002...），每个含描述 + 验收标准
- 不做的功能（边界约束）

### 3. 数据实体定义
- 核心数据实体（字段 + 类型 + 约束）
- 实体间关系

### 4. 接口契约框架
- API 端点框架（路径 + 方法 + 请求/响应概要）
- Ext 通信协议

### 5. 交互流程
- 核心用户操作流程
- 前端页面清单
- Ext 交互场景

### 6. 非功能需求
- 性能、安全、兼容性

## 红队审查重点

| 维度 | 典型缺陷 | 严重级别 |
|------|----------|----------|
| 技术栈模糊 | 未指定具体框架/ORM/端口 | high |
| 功能遗漏 | 用户流程中有未覆盖的分支 | high |
| 数据盲区 | 实体缺少关键字段 | high |
| 接口歧义 | API 描述导致前后端理解不一致 | high |
| 边界模糊 | "做个搜索"但未定义范围和排序 | medium |
| Ext 交互空白 | 未描述 Ext 与服务器通信协议 | high |

## 正反例参考

### ✅ 正例：技术栈选型明确
- 后端: Node.js 18 + Express 4 + Prisma ORM
- 数据库: PostgreSQL 15 (端口 5432)
- 前端: React 18 + Vite
- API 端口: 3000
- Ext: Manifest V3, REST API 通信

### ❌ 反例：技术栈模糊
- "用现代框架"——未指定具体框架 → 红队 will flag as high

### ✅ 正例：功能边界清晰
- F-001 用户注册：提交邮箱+密码 → 创建账户 → 返回 JWT。验收：Token 可用于后续 API 调用。

### ❌ 反例：功能边界模糊
- "做个用户管理功能"——无 ID、无验收标准 → 红队 will flag as high
