# 前端架构质量原则

> 本文档是前端设计师和前端工程师的**质量北极星**。设计与实现决策必须以此为准绳，红队审查以此为对抗基准。

## 核心信条

**用户不关心你的技术栈，只关心好不好看、好不好用。前端工程师首先是体验设计师，其次才是代码工程师。**

---

## 第 1 原则：设计系统先行——先定 Token，再画页面

### 为什么
没有设计系统的前端必然走向"每个页面风格不同"的混乱。设计系统（Design System）用 Token 体系统一颜色/字体/间距/阴影，确保全站视觉一致性。

### 怎么做
```
/* tokens.css — 全站唯一的设计令牌 */
:root {
  /* 色彩 */
  --color-primary: #4F46E5;     /* 主色 */
  --color-text: #1F2937;        /* 正文（非纯黑） */
  --color-text-secondary: #6B7280;
  --color-bg: #FFFFFF;
  --color-bg-muted: #F9FAFB;
  --color-danger: #EF4444;
  --color-success: #10B981;
  --color-border: #E5E7EB;

  /* 字体 */
  --font-sans: 'Inter', system-ui, sans-serif;
  --font-mono: 'Fira Code', monospace;
  --text-xs: 0.75rem;   /* 12px */
  --text-sm: 0.875rem;  /* 14px */
  --text-base: 1rem;    /* 16px */
  --text-lg: 1.125rem;  /* 18px */
  --text-xl: 1.25rem;   /* 20px */
  --text-2xl: 1.5rem;   /* 24px */

  /* 间距（8px 栅格系统） */
  --space-1: 0.25rem;  /* 4px */
  --space-2: 0.5rem;   /* 8px */
  --space-3: 0.75rem;  /* 12px */
  --space-4: 1rem;     /* 16px */
  --space-6: 1.5rem;   /* 24px */
  --space-8: 2rem;     /* 32px */

  /* 圆角 */
  --radius-sm: 4px;
  --radius-md: 8px;
  --radius-lg: 12px;

  /* 阴影 */
  --shadow-sm: 0 1px 2px rgba(0,0,0,0.05);
  --shadow-md: 0 4px 6px rgba(0,0,0,0.1);
}
```

- **所有**样式值引用 Token，禁止散落写魔法数字
- 配色不超过 1 主色 + 1 辅色 + 语义色（danger/success/warning）
- 字体不超过 2 种（正文 + 等宽）
- 新增页面时只组合已有 Token，不引入新值

## 第 2 原则：美学法则——让用户"一眼觉得专业"

### 为什么
人的大脑在 0.1 秒内就形成了对网站的"好看/难看"判断。美学不是锦上添花，是信任建立的基础。

### 怎么做
- **视觉层次法则**：每个页面有且只有一个**视觉焦点**（最重要的操作/内容），用大小区分主次
- **留白即呼吸**：元素间距 ≥ 内容本身的 1/3，拥挤 = 业余感
- **对比度**：文字与背景对比度 ≥ 4.5:1（WCAG AA），正文不用浅灰色
- **对齐即秩序**：所有元素遵循栅格对齐，不随意偏移
- **配色心理学**：蓝/绿 = 信任/安全（金融/医疗），橙/红 = 活力/紧迫（电商/促销）
- **图标语义化**：用图标辅助文字，但不替代文字（纯图标按钮必须有 tooltip）

### 决策框架与检查清单
- [ ] 页面有一个明确的视觉焦点吗？
- [ ] 留白是否充足（不拥挤）？
- [ ] 文字对比度是否 ≥ 4.5:1？
- [ ] 配色是否不超过 3 种主色？
- [ ] 按钮是否有清晰的主次区分（primary vs secondary）？

## 第 3 原则：原子设计——从分子到页面，可复用可组合

### 为什么
一个 500 行的页面组件无法复用、无法测试、无法维护。原子设计（Atomic Design）让 UI 像乐高一样可组合。

### 怎么做
```
components/
  atoms/        # 原子：最小不可分单元
    Button/
    Input/
    Badge/
    Avatar/
  molecules/    # 分子：2+ 原子组合
    SearchBar/    # Input + Button
    FormField/    # Label + Input + ErrorText
  organisms/    # 组织：复杂的 UI 区块
    Header/
    ProductCard/
    CommentSection/
  templates/    # 模板：页面骨架
    DashboardLayout/
    AuthLayout/
  pages/        # 页面：模板 + 数据
    Dashboard/
    Login/
```

- 原子层零业务逻辑，纯展示
- 分子层可少量业务逻辑（如表单验证）
- 页面层负责数据获取和组装，不写复杂 UI

## 第 4 原则：状态机思维——UI 是状态的函数

### 为什么
散落的 boolean 状态（isLoading / isError / isSuccess）组合爆炸，迟早出 bug。状态机用有限状态模型让 UI 行为可预测。

### 怎么做
```
// ❌ 散落的 boolean（4 个状态 × 2 = 16 种组合，多数无效）
{ isLoading, isError, isSuccess, data }

// ✅ 状态机（4 个状态，只有定义的转换路径）
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: E }
```

- 异步操作用状态机：idle → loading → success/error
- 用 XState 或自定义 reducer 管理复杂状态流转
- 每个状态有对应的 UI 渲染（加载中/空状态/错误/成功）

## 第 5 原则：性能预算——首屏 3 秒是硬约束

### 为什么
页面加载每慢 1 秒，转化率下降 7%。性能不是"优化阶段"的事，是"设计阶段"的约束。

### 怎么做
- **代码分割**：路由级 lazy loading，首屏只加载必要代码
- **图片优化**：WebP 格式 + 懒加载 + 响应式图片（srcset）
- **打包体积**：单 chunk 不超过 200KB（gzip 后），大依赖用动态 import
- **渲染性能**：长列表用虚拟滚动（react-window），避免不必要的 re-render（memo/useMemo/useCallback）
- **骨架屏**：加载中显示骨架屏，而非空白或 spinner（感知性能 > 实际性能）

### 决策框架与检查清单
- [ ] 首屏加载（LCP）< 3 秒？
- [ ] 是否做了路由级代码分割？
- [ ] 图片是否 WebP + 懒加载？
- [ ] 长列表是否虚拟滚动？
- [ ] 是否有骨架屏？

## 第 6 原则：可访问性——为所有人设计

### 为什么
全球 15% 人口有某种形式的残障。可访问性不是"可选功能"，是"基本人权"。且 SEO 也依赖 a11y。

### 怎么做
- 表单元素必须关联 label（`<label htmlFor>`）
- 图片必须有 alt 属性（装饰性图片用 `alt=""`）
- 键盘可完整导航（tab 顺序合理，焦点可见）
- 颜色对比度 ≥ 4.5:1（WCAG AA）
- 交互区域 ≥ 44px（触摸友好）
- 动态内容用 aria-live 通知屏幕阅读器

## 质量红线（绝对不做）

| 红线 | 理由 |
|------|------|
| 用纯黑 `#000000` 做文字色 | 对比度过高导致视觉疲劳，用 `#1F2937` |
| 内联样式 `style={{}}` | 无法复用、无法维护，用 CSS Modules/Tailwind |
| `!important` 强制覆盖 | 说明样式架构有问题，重构而非强覆盖 |
| z-index 混乱 | 用层级 Token（dropdown: 1000, modal: 2000, toast: 3000） |
| console.log 留在生产代码 | 用专业日志工具，生产环境移除 |
| 不处理加载/错误状态 | 每个 async 都要有 loading + error UI |
